# RAK10724 battery-powered MeshCore repeater

Build target: `RAK_10724_repeater`  
Branch: `PowerSaving-v17-rak10724`

## Hardware and source

This target is for the **battery-powered RAK10724 kit**: RAK19007 base,
RAK3401 nRF52840 core and RAK13302 SX1262/SKY66122 high-power radio.
It reuses the upstream RAK3401 board, battery ADC, flash/SoftDevice layout
and radio pins. It is not a RAK4631 target and does not create a different
bootloader contract merely because the kit has a different product number.

Source is pinned to IoTThinks `PowerSaving-v17` commit
`78e134b2ba08935b9c7639962819e257cdcf415c` (MeshCore 1.17.1).
The latest EasySkyMesh release page is `PowerSaving17.1`, updated with
PowerSaving 17.1.5 notes. This source tip includes subsequent fixes/default
changes; it is not claimed to be identical to a previously published binary.

## Features

- Upstream MCU idle power saving and SX1262 RXPSv2, with persistent CLI controls.
- Existing #batteryinfo channel/key and node-name prefix from our firmware fork.
- Battery voltage from the **RAK3401 ADC**, plus the existing linear 3.0–4.2 V
  percentage curve and rounding, using the original `battery=3.50v 42%`
  text format. Percentage is an estimate, not a fuel gauge. No LOW/OK labels,
  threshold or low-battery alarm policy is added. Unknown/zero battery is `na`.
- RAK1901/SHTC3 temperature and humidity at fixed I2C address `0x70`.
  Channel posts show Fahrenheit (for example `temp=77.0F`); standard binary
  MeshCore temperature telemetry remains Celsius as required by its protocol.
- INA260 bus voltage, signed current and signed-direction power, default
  address `0x40`. Adjust `TELEM_INA260_ADDRESS` to match address jumpers.
- Both sensors are also available via ordinary MeshCore environmental telemetry.
  LPP current is amperes; LPP power is unsigned whole watts. BatteryInfo text
  retains signed mA and mW for useful low-power resolution. Text power sign
  follows the measured current direction; wiring determines its meaning.
- Missing/failed sensor data is omitted from binary telemetry and `na` in text.
  CPU die temperature is not substituted for missing RAK1901 ambient temperature.
- Headless build: no display, GPS probing, unrelated sensors or BSEC dependency.

## Posting cadence

As in our existing BatteryInfo firmware, successful manual and scheduled
**flood adverts** enqueue one BatteryInfo group-text post. Local/zero-hop
adverts never trigger a BatteryInfo flood. Adverts retain the current scoped
routing API; BatteryInfo group text retains our existing unscoped flooding and
configured path-hash width.

There is no extra battery polling/transmission timer or LOW alert. Upstream's
fresh-install scheduled flood interval remains **47 hours**. Set an appropriate
cadence explicitly, for example `set flood.advert.interval 3` (three hours).
The upstream CLI permits 3–168 hours or 0 to disable scheduled floods. `advert`
sends a manual flood advert/post; `advert.zerohop` must send only a local advert.

The group message is bounded for encryption/header/name overhead. If a complete
body cannot fit, it is dropped rather than emitting a truncated value or unit.

## Power and wiring

Fit the RAK1901 in a compatible WisBlock sensor slot. Connect the INA260 logic
side to **3.3 V, ground and the same I2C bus**, with suitable pull-ups; the
RAK3401 variant configures SDA/SCL through its existing board pin definitions.
Do not apply INA bus voltage to an MCU/I2C pin. Place the INA260 current path in
series with the circuit you intend to measure and observe its board ratings.
INA260 bus voltage is intentionally NOT used as battery voltage: it could be
monitoring the input, solar feed or load, depending on wiring.

SHTC3 uses low-power one-shot conversion, validates both CRCs, and is returned
to sleep even after a failed measurement. This target avoids the Adafruit
SHTC3 driver's unbounded read-retry loop. INA260 uses one-shot voltage/current
conversion with checked register transactions, bounded ready polling, overflow
rejection and power-down after sampling. These snapshots are on-demand, not
continuous monitoring or integrated energy/coulomb measurements.

**Never switch WB_IO2/PIN_3V3_EN off to save sensor power.** It also enables the
RAK13302's 5 V PA supply. The upstream battery-kit fix keeping that shared rail
high during radio operation is preserved. A battery must be connected for the
kit to reach 1 W, and the correct LoRa antenna must be connected before power.
SX1262 drive stays at the upstream 22 dBm setting; the amplifier provides the
kit's higher RF output. Actual output and legal limits require verification.

## Setup

The current pinned source defaults fresh installs to power saving ON and
RXPS enabled (level 6, preamble 16). Existing saved settings override defaults.
Check the actual device and use upstream controls:

```text
powersaving
get radio.rxps
powersaving on
set radio.rxps balanced
get flood.advert.interval
set flood.advert.interval 3
advert
advert.zerohop
```

Follow upstream advice to reboot after changing RXPS settings. Do not enable
low-voltage system-off/bootlock merely to enable ordinary power saving; this
build does not enable `NRF52_POWER_MANAGEMENT` shutdown policy.

The build inherits upstream RF defaults (869.618 MHz, BW62.5, SF8). Configure
your actual network frequency/BW/SF/CR and legal TX settings **before deployment**;
this is not a region-specific preset. Change the upstream default admin
password (`password`) before operating the repeater. Saved settings/identity
may survive an application update; flashing is not a factory reset.

## Build and install

```sh
pio run -e RAK_10724_repeater
pio run -e RAK_10724_repeater -t create_uf2
pio test -e native
python3 scripts/check_rak10724_routing.py
pio run -e RAK_3401_repeater
python3 scripts/package_rak10724.py --output /path/to/output
```

Sensor presence is detected at boot. Reboot after fitting a sensor that was
absent at startup; a previously detected sensor can recover after transient
read failures. Configure the INA260 address before building.

Local verification completed: both firmware targets compiled; all 89 native
test cases passed, including 12 RAK10724 cases; the routing guard passed.
Packaging checks validated the nRF52840 UF2 family/application range and proved
UF2 payload bytes match the serial-DFU application's binary. This remains
software/artifact verification, not a physical-kit result.

Use `.pio/build/RAK_10724_repeater/firmware.uf2` with the board's compatible
UF2 bootloader (double-reset into bootloader and copy the UF2 onto its drive).
The generated `firmware.zip` is a serial-DFU application package.
These are application updates using the inherited S140 6.1.1 layout, not a
bootloader installer. Preserve the existing bootloader/recovery path.

## Verification boundary

Local target and ordinary RAK3401 regression builds, native tests and the
source-level flood/zero-hop routing checks are required. The routing script
is a source guard, not a simulated or actual RF test.

On hardware, verify:
1. USB CLI boots with the expected version; settings and identity survive reboot.
2. ADC battery voltage agrees with a meter and the original percentage estimate is shown.
3. RAK1901 readings agree with a reference and no-sensor/NACK behavior stays responsive.
4. INA260 address, voltage, current sign and power agree with wiring/reference measurements.
5. Flood advert produces one channel post; zero-hop produces no post or flood.
6. Measure idle/RX/TX current with RXPS off/on, exercise receive/CAD/TX recovery,
   and confirm the 1 W boost rail stays enabled.

No physical kit was flashed or measured during this implementation. Compiler
success and injected transport tests do not prove RF output, battery calibration,
sensor accuracy, RF delivery or actual power savings.
